# LLM 라우팅 에이전트 실험 규약

LLM을 돌리기 전에 고정한 규약이다. 결과를 본 뒤 바꾼 항목은 이 문서 끝의 "변경 기록"에 이유와 함께 남긴다.

## 1. 질문과 비교

PPO-GCN과 기존 기준 방법은 운영자가 텍스트로 주는 제약(예정 정비, 혼잡, 지역 정책 등)을 이해하지 못한다.
LLM 에이전트가 그 역할을 할 수 있는지 WCNC 2027 투고 논문의 설정과 지표로 잰다.

1. 제약 없음: LLM 에이전트 대 PPO-GCN과 기준 방법 5종(Dijkstra, PRP, Cost-Greedy, Adapted ISASR, Lifetime)
2. 제약 있음: LLM 에이전트(도구 없음). 제약을 모르는 기존 방법이 같은 조건에서 얼마나 어기는지도 함께 잰다.
3. 제약 있음 + 도구: 같은 LLM이 Python 도구(검증, 주변 확장, 구간 재계산, 지역 조회)를 쓸 때

## 2. 평가 데이터

- WCNC 고정 시험셋 3,600개(경로 쌍 3 × 유지 시간 X 5 × 도착 시각 240)에서
  도착 시각 12개(240개를 20개씩 나눈 묶음의 가운데, 인덱스 10, 30, …, 230)를 고른 **180개**
  (3 × 5 × 12). 도착 시각(초): 251, 729, 1208, 1686, 2164, 2642, 3121, 3599, 4077, 4555, 5034, 5512.
- 시뮬레이터, 초기 링크 배치, 지상 접촉 계산 범위는 고정 시험셋 실행과 같다(`scripts/run_llm_routing.py`).
- 같은 180개에서 기존 방법의 완주율(%)과 전체 3,600개 값:

  | 방법 | 3,600개 | 180개 |
  |---|---:|---:|
  | PPO-GCN (시드 3개) | 92.56 | 92.96 |
  | Lifetime | 83.53 | 80.56 |
  | Adapted ISASR | 82.11 | 80.00 |
  | Cost-Greedy | 80.64 | 76.11 |
  | PRP | 72.39 | 72.78 |
  | Dijkstra | 51.14 | 59.44 |

  순위는 같고 값은 최대 8.3%p 다르다(표본 크기에서 예상되는 범위). 결과 표는 모든 방법의 180개 값과
  윌슨 95% 신뢰구간을 쓰고, 논문의 3,600개 값은 참고 열로 둔다.

## 3. 결정 시점과 실행

- `SessionEnvironment.run(method, request)`를 그대로 쓴다. 경로 계산기에 `"llm"` 방식을 더했을 뿐이라
  처음 경로와 매 재경로(가장 먼저 끊길 링크보다 20초 앞)에서 LLM이 결정하는 시점이 PPO-GCN과 같다.
- 재현 확인: LLM 자리에 Dijkstra 경로를 그대로 돌려주는 모델을 넣으면 180개 모두에서 설정 성공, 완주,
  끊긴 시간, 재구성, 새 ISL, 경로 km, 가용도, 결정 횟수가 고정 시험셋의 Dijkstra 결과와 같다
  (`tests/test_llm_routing.py`).

## 4. LLM 입력과 출력

- 입력: 세션(출발·도착 지상국, 결정 시각, 남은 유지 시간), 공통 접속·도착 위성, **Dijkstra 경로**
  (논문의 Dijkstra = `raw`), 그 경로에서 **1홉 이내 위성** 목록(위도·경도, 그 위성들 사이 링크의 종류
  P/A/N, 남은 접촉 시간, 길이), 제약이 있으면 운영자 텍스트.
- Dijkstra 경로는 홉별 표(링크 종류, 남은 접촉 시간)로도 준다. 위도·경도는 운영자 조건이 있을 때만 준다.
- 출력: 먼저 `Check:` 뒤에 자기 경로의 각 홉을 목록에서 찾아 적고(스스로 확인), 마지막에
  `{"route": [접속 위성 … 도착 위성], "reason": "한 문장"}`. 홉 단위가 아니라 지상국 간 전체 경로 한 번.

## 5. 검증과 실패 처리

- 구조 규칙만 검사한다: 공통 접속 위성에서 시작해 공통 도착 위성에서 끝남, 연속 위성 사이에 지금 가능한
  링크가 있음, 같은 위성 반복 없음, 한 위성에서 위성 간(A/N) 링크로 들어와 나가지 않음.
  Dijkstra 경로가 지키는 규칙과 같다.
- 링크가 세션보다 먼저 끊기는지, 새 링크가 설정 전에 끊기는지는 시뮬레이터가 판정한다(Dijkstra와 같은 기준).
  이런 링크는 경고로 기록한다.
- 구조 규칙을 어긴 답, JSON이 아닌 답, API 오류는 Dijkstra 경로로 대신 실행하고 "무효 수정"으로 센다.

## 6. 모델과 호출 설정

- 모든 모델을 OpenAI 호환 Chat Completions API 한 경로로 부른다. 같은 시스템 프롬프트, temperature 0,
  seed 0, max_tokens 1024. Claude Code나 LangChain처럼 모델 밖 장치가 들어가는 실행기는 쓰지 않는다.
- 최종 결과: GPT-4o. 개발과 디버깅: GPT-4o mini. gpt-oss 계열은 쓰지 않는다. 로컬 소형 모델(Ollama)은 나중에 같은 경로로 추가한다.

## 7. 지표

- 논문 지표: 설정 성공, strict session completion, 가용도, 끊긴 시간, 재구성 수, 새 ISL 수, 경로 km
- 에이전트 지표: 유효 수정 비율, 경로를 바꾼 비율, 경고 링크 수, 결정당 토큰과 시간, 비용
- 제약 지표(제약을 넣을 때 정의): 제약별 준수율, 제약을 모두 지키면서 완주한 비율, 거리·지연 증가

## 8. 개발용 데이터

프롬프트 작업은 평가 180개와 겹치지 않는 도착 시각(인덱스 0, 20, …, 220)의 요청으로만 한다
(`--split dev`). 평가 180개는 프롬프트를 확정한 뒤 한 번만 돌린다.

## 9. 진행 순서

1. 제약 없음: GPT-4o mini로 개발 → GPT-4o로 180개
2. 제약 6종을 하나씩 넣는다(예정 정비·고장, 핫스팟, 지역 금지·경유, 지상국 안테나 장애, PAT 재지향 상한,
   지연 상한). 제약마다 텍스트, 세계 상태 반영, 준수 지표, 도구를 정한 뒤 2와 3을 비교한다.
   진행한 것: 1(10절), 2(11절), 3 지역 금지(13절), 5(14절), 6(15절). 4 지상국 안테나 장애는 접속 위성 규칙을
   바꿔야 해서 보류했다. 지역 경유는 넣지 않았다.
3. 마지막으로 여러 조건을 한꺼번에 주고 LLM이 CP-SAT 모델을 작성하게 한다(12절).

## 10. 제약 1: 예정 정비(예고 없는 위성 중단)

- 시나리오(`scripts/make_scenarios.py maintenance`): 요청마다 요청 시각 Dijkstra 경로의 가운데 위성
  (접속·도착 위성 제외)이 시각 t0 + X/2에 정비로 꺼진다. 세션 도중에 꺼지도록 한 것이다. 운영자 텍스트
  3가지 표현을 요청 순서대로 돌려 쓴다.
- 세계 반영(`SessionEnvironment.set_outages`): 경로 계산기는 정비 시각 전까지 위성을 정상으로 보고(공지를
  모르므로), 그 뒤로는 위성의 링크가 사라진다. 시뮬레이터는 정비를 미리 알지 못해 앞당겨 재경로하지 않는다.
  정비 위성을 지나던 경로는 그 시각에 끊기고, 감지에 1초(가정)가 걸린 뒤 새 경로를 잡는다. 새 링크 설정
  20초도 끊긴 시간에 더한다. 예측 가능한 WCNC 사건(접촉 종료)의 처리는 그대로다.
- 정비가 없을 때 기준 방법 5개, PPO-GCN 시드 3개, 항등 LLM이 고정 결과를 180개 8개 지표에서 모두
  재현함을 확인했다.
- 추가 지표: 정비로 경로가 끊긴 세션 비율(`outage_hits` > 0), LLM 첫 결정이 정비 위성을 피했는지,
  무효가 된 제안이 정비 위성을 피하려 했는지(원래 제안 경로를 기록한다).
- 개발용 관찰(개발용 12개, GPT-4o, 도구 없음): 첫 결정에서 정비 위성을 피한 경우 1/12, 유효 13/24.
  우회로를 지어낸 링크로 짜다 무효가 됐다. 주어진 1홉 주변 정보 안에 정비 위성을 피하는 올바른 경로는
  평가용·개발용 180개 모두에 존재함을 계산으로 확인했다(입력이 부족해서 생긴 실패가 아님).

- 도구 조건(③, `--tools`, `llm_routing/tools.py`): 입력과 결정 시점은 ②와 같고 도구 3개를 준다.
  `check_route`(규칙 검사, 홉별 링크 종류와 남은 접촉, 세션보다 먼저 끝나는 링크, 피할 위성 포함 여부),
  `find_route`(망 전체에서 v3 규칙을 지키며 지정 위성을 피하는 경로, 선택적으로 링크 최소 수명, 목표는 최소 홉
  또는 최장 접촉), `submit_route`(규칙 위반이면 이유와 함께 거절). 도구는 운영자 텍스트를 읽지 않는다.
  호출은 결정당 최대 8회, 제출이 없으면 Dijkstra로 대신 실행한다.
- 개발용 관찰(개발용 12개, GPT-4o, 도구 있음): 첫 결정 회피 12/12, 유효 15/15, 정비로 끊김 0, 완주 11/12,
  결정당 약 $0.057. 이 설정으로 확정했다.
- 노출 분석(`results_llm/maintenance_exposure.md`): 정비 위성을 Dijkstra 경로에서 골랐기 때문에 경로가 Dijkstra와
  다른 방법은 우연히 피할 수 있다. 첫 경로가 정비 위성을 쓴 세션의 완주는 텍스트를 못 읽는 방법 모두 0~6%이고,
  PPO-GCN의 높은 완주는 첫 경로의 86%가 우연히 그 위성을 피한 데서 온다. 도구가 있는 LLM은 공지를 읽고
  92%(GPT-4o)와 100%(mini)를 피했다.

## 11. 제약 2: 트래픽 핫스팟(가능하면 피함)

- 시나리오(`make_scenarios.py hotspot`): 요청 시각 Dijkstra 경로의 중간 위성(접속·도착 제외)이 가장 많이 지나는
  지역. 180개 모두 지정. 세션 내내 완전히 피할 수 있는 경우 137/180.
- 프롬프트에 지역의 위도·경도 범위를 함께 준다(평가 기준과 같은 범위, 도구 유무와 무관). 운영자 조건이 있으면
  "이 세션에서 지금까지 켠 링크 수"도 준다(이 줄은 제약 2부터 들어갔고, 제약 1 실행에는 없었다).
- 지표(`llm_routing/compliance.py`, 모든 방법의 기록된 경로를 세션 동안 10초 간격으로 따라감): 중간 위성이 그 지역
  위에 있던 시간 비율, 그 지역 위 중간 위성 수, 평균 지연(ms). 완주 등 논문 지표도 함께 본다.
- 모델: API 비용 때문에 제약 2부터 GPT-4o mini만 쓴다(제약 1은 GPT-4o와 mini 모두).
- 도구 변경(개발 단계): `find_route`에 지역 회피(`avoid_regions`, 세션 동안 그 지역에 들어오는 위성까지 제외)와
  최소화(`prefer_avoid_regions`), 목표 `fewest_new_links`, `shortest_distance`를 더했고, `check_route`가 지역 통과,
  새 링크 수, 지금 지연을 알려 준다. 접속·도착 위성은 지역 때문에 제외하지 않는다(모든 방법에 고정). 완전 회피가
  불가능하면 도구가 최소화 옵션을 안내한다. 제약 1의 도구 실행은 이 확장 전의 도구로 했다.
- 개발용 관찰(개발용 12개, mini): 도구 없음 지역 시간 91.1%, 도구 있음 27.3%(지연 51.1 → 70.2 ms). 완전 회피가
  불가능한 결정에서 mini가 최소화 옵션을 쓰지 않고 제출을 못 한 경우가 16번 중 7번 남았다(모델 한계로 기록).

## 12. 예정: 다중 제약 + LLM 정식화(CP-SAT 코드 작성)

LLM이 텍스트 조건을 최적화 모델로 정식화하고 solver와 연계하는 능력을 보기 위해 마지막 실험으로 넣는다.
- 제약 여러 개(지역 금지, 지연 상한, 새 링크 상한, 링크 수명)를 동시에 지키는 경로는 자원 제약이 여러 개인
  최단 경로 문제(일반적으로 NP-hard)라 solver가 필요하다. 단일 제약 실험의 경로 탐색 도구로는 모두를 보장하지 못한다.
- 기준: 저자가 작성한 CP-SAT 모델로 조건별 최적값을 구한다.
- 본실험(나): LLM이 운영자 텍스트와 데이터 설명을 보고 OR-Tools CP-SAT 코드를 작성하고, 실행 결과(오류, 해 없음)를
  보고 고친다. 채점은 기준 최적값 일치, 조건 준수(준수 평가기), 시뮬레이터 완주.
- 규모: 다중 제약 시나리오 약 60개, GPT-4o와 GPT-4o mini. 단일 제약 실험을 모두 끝낸 뒤 진행한다.

## 13. 제약 3: 지역 통과 금지(반드시 피함)

- 시나리오(`make_scenarios.py avoid`): 요청 시각 Dijkstra 경로의 중간 위성이 가장 많이 지나는 지역 가운데, 요청
  시각에 세션 내내 피하는 경로가 있는 첫 지역. 180개 중 167개(나머지 13개는 그런 지역이 없어 텍스트 없이 실행).
  운영자 텍스트 3가지 표현과 지역의 위도·경도 범위를 준다.
- 지표: 세션 동안 중간 위성이 그 지역 위에 한 번이라도 있었던 세션 비율(위반), 그 시간 비율.
- 개발용 관찰(개발용 12개, mini): 도구 없음 위반 100%. 도구 있음 9%(필수 인자 도구) → 55%(선택 인자 도구, 변경
  기록 4). 표본이 작고, 차이는 제출 실패 수(5 → 7/17)에서 왔다.
- 평가 결과(`results_llm/table_avoid.md`): 위반 Dijkstra 100%, mini 100%, mini + 도구 55.9%(지역 위 시간 90.6% →
  41.4%). mini가 모든 결정을 제출한 77개 세션의 위반은 14.3%, 한 번이라도 Dijkstra로 대신 실행된 84개는 94.0%다.
  재경로 시점에 완전 회피가 불가능하면 mini가 최소화 옵션을 쓰지 않고 제출하지 못한다(11절과 같은 한계).
- 비용 상한($2.2)으로 177개에서 멈췄고, 남은 3개(모두 600초 세션)를 `--request-ids`로 따로 실행해 합쳤다.
  요청은 서로 독립이다(`COMPLETED_IN_TWO_PARTS`).

## 14. 제약 5: PAT 재지향 상한(세션 전체 새 링크 수)

- 시나리오(`make_scenarios.py budget`): 상한 k = 요청 시각에 세션 시간만큼 유지되는 경로 중 새 링크가 가장 적은
  경로의 새 링크 수 + 1. 180개 모두 k = 1이다. 프롬프트에 "이 세션에서 지금까지 켠 링크 수"를 준다.
- 지표: 세션 전체 새 링크 수(시뮬레이터의 `dynamic_setups`)가 k를 넘은 세션 비율.
- 개발용 관찰(개발용 12개, mini): 도구 없음 위반 100%. 도구 있음 100%(필수 인자 도구, 지어낸 회피 조건 때문에
  제출 실패 10/18) → 50%(선택 인자 도구, 유효 15/15).
- 평가 결과(`results_llm/table_budget.md`): 위반 Dijkstra 100%, Cost-Greedy 13.3%(완주 76.1%), mini 99.4%,
  mini + 도구 22.8%(완주 96.7%, 유효 100%). 남은 위반은 모두 제출한 경로에서 나왔다. 재경로마다 새 링크가 더해지는
  세션 단위 예산을 mini가 관리하지 못한 경우다.

## 15. 제약 6: 지연 상한

- 시나리오(`make_scenarios.py latency`): 상한 = 요청 시각 최단 거리 경로 지연의 1.15배를 5 ms 단위로 올림
  (30~85 ms). 지연 = (지상 링크 + 경로 길이) / 광속, 단방향.
- 지표: 세션 동안 10초 간격으로 잰 지연이 상한을 넘은 시간 비율.
- 개발용 관찰(개발용 12개, mini): 도구 없음 36%. 도구 있음 55%(필수 인자 도구, 제출 실패 10/17) → 3%(선택 인자
  도구, 유효 15/15).
- 평가 결과(`results_llm/table_latency.md`): 상한 초과 시간 Dijkstra 18.2%, PPO-GCN 52.3%, mini 21.6%,
  mini + 도구 12.5%(완주 83.9%, 유효 99.1%).

## 변경 기록

모두 평가 실행 전, 개발 단계의 변경이다.

1. 첫 시험(GPT-4o mini, 프롬프트 1판)을 실수로 평가 180개 중 12개에서 돌렸다. 결정 25번 중 유효 10번,
   바꾼 경로 1번. 이후 개발은 겹치지 않는 개발용 도착 시각으로만 했다(8절).
2. 프롬프트 2판: Dijkstra 홉별 표 추가, 경로 규칙 명시, "문제없으면 그대로", 조건이 없으면 위도·경도 제외.
   개발용 12개에서 GPT-4o mini는 유효 16/17이지만 바꾼 경로 0, GPT-4o는 유효 6/15, 바꾼 경로 2.
3. 프롬프트 3판: 답하기 전에 각 홉을 목록에서 찾아 적게 했다(도구 없는 자기 확인). 답은 마지막 JSON에서 읽는다.
   개발용 12개에서 GPT-4o 유효 17/19, 바꾼 경로 7, 완주 9/12(Dijkstra 8/12). 이 판으로 확정한다.
4. 도구 인자(제약 3·5·6 개발 중): `find_route`의 회피 목록 인자를 필수로 두었더니, 조건이 없는데도 mini가 칸을 채우려고
   회피 지역을 지어냈다(제약 없음 + 도구 실행에서 `find_route` 2,280번 중 2,260번, 결정 407개 중 264개 제출 실패).
   `objective`만 필수로 바꿨다. 그 실행은 `gpt-4o-mini_none_tools_v1`로 남기고 다시 실행했다(유효 143/407 →
   338/344, 완주 61.1% → 78.9%). 제약 1 도구 실행은 지역 인자가 생기기 전 도구로 했고(실패 0), 제약 2 도구
   실행은 필수 인자 도구로 했다. 제약 2 기록에서 지어낸 지역은 0번이라 다시 실행하지 않았다(비용).
5. 위도·경도: 제약 3부터는 지역 조건이 있는 시나리오에만 준다(제약 1·2는 운영자 조건이 있으면 줬다). 지역과 상관없는
   조건에서 입력 토큰을 줄이기 위해서다.
6. 비용 보호: API가 크레딧 부족으로 거절하면 Dijkstra로 대신하지 않고 실행을 멈추고 `INCOMPLETE`로 표시한다.
   실행마다 비용 상한(`--max-usd`)을 둔다.
